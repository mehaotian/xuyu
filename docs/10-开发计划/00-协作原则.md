# 协作原则

## 1. 先读，再改

开始任何代码工作前，先阅读：

1. `docs/README.md`；
2. 当前阶段计划；
3. 当前阶段的实现记录；
4. 根目录 `AGENTS.md` 或编辑器规则。

如果发现文档与代码不一致，先记录差异，再决定是否修改；不要默默用代码覆盖文档。

## 2. 一步一停

一次只做一个小目标。例如：

- 创建项目骨架；
- 定义 Token 类型；
- 识别一个关键字；
- 读取一个整数；
- 解析一条赋值语句。

完成后必须报告：做了什么、没有做什么、如何验证、下一步是什么。没有用户确认，不自动跨到下一步。

## 3. 代码要让后来者看得懂

- 函数和类型命名保持一致；
- 复杂逻辑前写一段简短中文说明；
- 注释解释“为什么”，不重复描述代码表面动作；
- 不使用夸张、营销化或模板化的 AI 口吻；
- 注释不写未验证的性能、兼容性和安全承诺；
- 每个重要实现都配一个最小示例或测试。

## 4. 小范围修改

- 不为了整理而重写无关代码；
- 不批量引入未来阶段的目录和依赖；
- 不改变已经记录的实验结论，除非同时更新决策记录；
- 发现设计问题时优先写实验或 RFC，不直接扩大当前实现。

## 5. 讨论方式

讨论语法时提供：示例、期望含义、冲突情况和替代方案。只说“更自然”“更现代”不够作为设计依据。

讨论实现时说明：输入、输出、错误、边界和测试。没有测试的“应该可以”不能当作完成。

## 6. 提交和记录

提交信息和实现记录使用中文，必要时保留 Lexer、Parser、AST、IR 等通用术语。每个阶段结束时整理一次阶段总结，不要求每个小步骤都提交 Git，但必须保留可回看的记录。
