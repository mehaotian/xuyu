# 语句边界实验

**日期：** 2026-09-21
**状态：** 已完成设计实验，尚未修改 Lexer

## 1. 实验问题

当前 Lexer 会跳过换行，因此 Parser 无法区分两条相邻语句：

```text
设置 名字 = 1
设置 年龄 = 18
```

在支持多条语句前，必须先确定语句边界。

## 2. 方案比较

### 方案 A：换行作为语句边界

```text
设置 名字 = 1
设置 年龄 = 18
```

**优点：** 源码简洁，符合脚本和配置类代码的阅读习惯；错误位置容易对应到实际行；不要求用户额外输入分号。
**问题：** 多行表达式、括号、字符串和注释加入后，需要规定哪些换行可以忽略。

### 方案 B：只依靠缩进和代码块

**优点：** 与后续条件、循环的代码块设计一致。
**问题：** 顶层连续语句仍需要结束规则；如果把所有换行都交给缩进处理，错误恢复和单行表达式会变复杂。

### 方案 C：使用分号

```text
设置 名字 = 1；设置 年龄 = 18；
```

**优点：** 规则明确，跨行和压缩格式简单。
**问题：** 增加输入负担，与项目希望保持自然中文代码的方向不一致；复制中文文本时也更容易出现全角/半角差异。

### 方案 D：换行为主，分号暂缓

允许换行结束语句，未来如有需要再考虑分号作为可选显式分隔符。

**优点：** 保留简洁源码，也为机器生成和特殊场景留下空间。
**问题：** 需要在规范中清楚定义括号、文字和注释中的换行行为。

## 3. 临时决定

阶段 0.10 建议采用 **方案 D**：

1. Lexer 产生 `换行` Token；
2. Parser 在顶层把换行作为语句分隔；
3. 文件开头、文件结尾和连续空行可以被 Parser 忽略；
4. 当前没有括号表达式，因此暂不处理“括号内换行”；
5. 分号不进入当前实现，是否支持留到真实代码实验后再决定；
6. 缩进 Token 留到代码块实现时单独设计，不用它解决顶层语句边界。

这只是下一步实现的实验决定，不是最终语言规范冻结。

## 4. 预期测试样例

### 两条语句

```text
设置 名字 = 1
设置 年龄 = 18
```

预期：产生两条赋值语句。

### 空行

```text

设置 名字 = 1


设置 年龄 = 18
```

预期：空行不产生语句。

### 文件末尾没有换行

```text
设置 名字 = 1
```

预期：EOF 可以结束最后一条语句。

## 5. 暂不解决的问题

- 括号内换行；
- 多行文字；
- 注释和注释后的换行；
- 自动插入语句结束符；
- 缩进错误和代码块 Token。
