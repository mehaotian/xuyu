# 阶段 0 结束评估

**日期：** 2026-09-21
**评估范围：** 从 `.中` 文件到变量环境的最小闭环

## 1. 已经完成

当前可以运行：

```text
设置 名字 = 1
```

并经过：

```text
文件读取
  -> Lexer
  -> Token
  -> Parser
  -> AST
  -> Interpreter
  -> 环境[名字=1]
```

已经具备：

- 可构建的 Go 项目；
- 中文 CLI 帮助、版本和运行命令；
- 中文标识符和一个中文关键字；
- 带位置的 Token 和语法错误；
- AST、解释器和变量环境的清晰边界；
- 单元测试、集成测试和可阅读的实现记录；
- 新参与者可以从文档和测试开始阅读。

## 2. 还没有完成

- 一个文件只能有一条赋值语句；
- 变量不能作为表达式被读取；
- 不能进行加减乘除和比较；
- 没有文字、布尔、列表、函数和输出语句；
- Lexer 当前会跳过换行，没有保留语句边界；
- CLI 还没有区分词法、语法和执行错误的退出码；
- 模块名、文件扩展名和关键字表仍是实验方案。

## 3. 当前结构是否适合继续

结论：**适合继续，但不适合马上堆叠更多语法。**

当前模块边界已经能够让后来者分别阅读 Lexer、Parser、AST、Interpreter 和 CLI。下一步最需要解决的是“一个文件如何表示多条语句”，这是语法和 Lexer 的共同基础。

## 4. 语句边界问题

当前输入：

```text
设置 名字 = 1
设置 年龄 = 18
```

Lexer 会跳过换行，Parser 只能看到两组连续 Token，无法可靠判断第一条语句在哪里结束。

在增加多条赋值前，必须先做一个小实验，比较以下方案：

1. Lexer 产生 `换行` Token，Parser 使用换行分隔语句；
2. 只使用缩进或块结构，不把普通换行作为语句边界；
3. 引入分号或其他显式分隔符；
4. 允许换行分隔，但在括号或表达式中继续换行。

当前不直接选定方案。先用小样本测试可读性、错误恢复和后续多行表达式影响。

## 5. 阶段判断

阶段 0 的“基础链路实验”已经完成，可以进入下一轮设计实验；阶段 0 的“语言能力”远未完成。这里的完成只表示：项目从想法变成了一个可运行、可测试、可阅读的最小实现。

## 6. 下一步决定

增加步骤 0.10：**语句边界实验**。

只研究换行和语句结束，不实现变量引用、表达式、条件或循环。实验有结论后，再决定如何支持多条赋值语句。
