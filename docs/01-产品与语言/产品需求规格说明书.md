# 产品需求规格说明书

**版本：** PRD v0.2（整理评审版）
**定位：** 个人发起、爱好者共建的中文编程语言实验项目
**范围：** 从语言实验器开始，逐步验证 CLI、标准库和工具链
**优先级：** P0 必须、P1 应该、P2 后续

> 本文是分阶段需求总表，不是第一步实施清单。当前开发只执行 [开发计划](../10-开发计划/README.md) 中标记为“当前步骤”的内容，完成后暂停评审。

## 1. 产品目标

### 1.1 第一阶段目标

先交付一个可阅读、可运行、可测试的语言实验器，参与者可以：

1. 编写中文源码并获得确定性解析和中文诊断；
2. 运行包含变量、函数、条件和循环的程序；
3. 阅读源码、测试和实现说明，理解每一层做了什么；
4. 在项目中提交一个小而完整的改动。

文件、JSON、格式化、测试、构建和独立发布属于后续阶段，不在第一步一次完成。

### 1.2 非目标

项目不承诺成为主流语言，也不以替代 Python、Go、Rust 为目标。早期不承诺：完整 GUI、完整调试器、泛型、宏、JIT、并发运行时、所有平台 Native、公共包生态、完整数据库驱动或成熟语言的全部能力。

## 3. 功能需求

### 3.1 语言核心（P0）

- UTF-8 源码输入；统一换行和错误位置计算。
- 中文、英文、数字和下划线标识符；数字不得作为首字符。
- 整数、小数、文字、布尔、空值五种基础类型。
- 列表、字典/映射、对象三种复合类型。
- 字面量、属性访问、函数调用、算术和比较表达式。
- 变量声明/赋值、函数、条件、条件循环、计数循环和显式集合遍历。
- 缩进代码块；编译器将缩进转换成明确的 Block AST。
- 导入模块和最小可见性规则。
- 中文关键字和中文诊断；英文符号保留在表达式中。

### 3.2 编译器与执行（P0）

- Lexer：输出带源码范围的 Token，非法字符必须可定位。
- Parser：输出稳定的 AST，并支持结构化错误恢复。
- 语义分析：名称解析、作用域、类型检查和控制流基本检查。
- 解释器：执行稳定 IR 或 AST；异常和资源错误可追踪到源码。
- CLI：`运行`、`检查`、`格式化`、`测试`、`构建`、`版本`、`帮助`。
- 编译结果必须与解释器的稳定测试一致。

### 3.3 项目与构建（P0/P1）

建议工程结构：

```text
我的项目/
├── 项目.toml
├── 主程序.中
├── 源码/
├── 测试/
├── 资源/
└── 锁定文件
```

P0 支持单模块和本地路径依赖；P1 再支持版本依赖和注册表。

项目清单至少包含：项目名、语言版本、入口文件、目标平台、依赖、构建配置和许可证。

### 3.4 标准库（P0/P1）

P0：文字、列表、映射、文件、目录、路径、JSON、时间、随机数、命令行参数、日志。
P1：HTTP 客户端/服务端、正则、进程、数据库接口、异步 I/O。
P2：图形界面、科学计算、游戏引擎、平台专用 API。

标准库 API 必须有中文文档、错误类型、示例和跨平台行为说明。库 API 不应依赖“魔法猜测”。

### 3.5 诊断系统（P0）

每条诊断至少包含：

- 稳定错误编号；
- 严重级别（错误、警告、提示）；
- 文件、行、列和源码范围；
- 期望内容与实际内容；
- 中文解释和最小修复建议；
- 可选机器可读 JSON 输出。

示例：

```text
错误 C-TYPE-001：类型不匹配
位置：主程序.中，第 3 行，第 8 列
期望：整数
实际：文字「100」
建议：删除引号，或将目标字段声明为文字。
```

编译器不得自动接受错别字、同音字或 AI 改写结果。IDE 只能提供候选操作，用户必须确认。

### 3.6 IDE 与 Language Server（P1）

第一阶段优先支持 VS Code 扩展和 LSP：

- 语法高亮；
- 诊断和悬浮说明；
- 中文关键字、API、符号补全；
- 拼音和模糊搜索；
- 跳转定义、查找引用、重命名；
- 格式化和项目级符号索引。

断点、变量查看和完整调试器作为 P2，前提是 Native/WASM 后端已有稳定调试信息。

### 3.7 包管理和发布（P1/P2）

P1：本地模块、路径依赖、锁定文件和离线构建。
P2：公共注册表、版本约束、校验和、镜像、私有仓库、许可证和供应链审计。

发布命令需要明确目标、产物目录、运行时打包方式、系统依赖和可复现构建信息。

## 4. 非功能需求

### 4.1 确定性与可靠性

- 无网络、无 AI、无输入法状态时，编译结果必须一致。
- 编译器、解释器和格式化器在同一版本规范下工作。
- 诊断范围和错误编号在补丁版本内保持兼容。

### 4.2 性能目标

MVP 不以极限性能为目标，但需建立基线：

- 1 万行以内项目的检查和解释启动时间可接受；
- 中文源码在 Lexer 后转换为 Symbol ID，运行时不反复比较长字符串；
- 大文件编辑时 IDE 诊断不能因全量解析明显卡顿；
- 每次性能优化必须有可重复基准。

### 4.3 可移植性

先确定一个主开发平台和一个发布平台；扩展到其他平台必须有 CI、标准库行为测试和产物验证。不要在没有平台维护能力时宣称“全平台支持”。

### 4.4 安全性

- 包和构建输入必须支持校验和与来源记录；
- 默认禁止远程导入和构建脚本执行；
- FFI、进程、文件和网络权限应可见、可限制；
- 编译器服务处理不可信源码时不得执行用户程序；
- 错误信息不得泄露环境变量、密钥和绝对路径（可配置）。

### 4.5 可维护性

- 规范、实现、测试和示例版本绑定；
- AST、IR 和诊断采用稳定序列化格式或版本标记；
- 核心组件避免隐式全局状态；
- 外部工具链版本进入构建元数据。

## 5. 端到端工作流

```text
安装开发工具
    ↓
创建项目
    ↓
编辑中文源码
    ↓

```

## 6. MVP 验收案例

### 案例 A：基础程序

```text
定义 主程序：
    设置 名字 = 「世界」
    输出 「你好，」 + 名字
```

预期：格式化、检查、解释运行成功，输出 `你好，世界`。

### 案例 B：类型错误

```text
定义 玩家：
    生命：整数 = 100

定义 主程序：
    设置 玩家.生命 = 「很多」
```

预期：不执行程序，报告中文类型错误、源码范围、期望类型和修复建议。

### 案例 C：显式集合遍历

```text
定义 主程序：
    设置 用户列表 = [「甲」, 「乙」]
    遍历 用户列表 为 用户：
        输出 用户
```

预期：两次输出，循环变量在嵌套场景中不与外层混淆。

### 案例 D：独立产物

项目构建后，在干净目标环境执行产物；记录是否需要额外运行时、动态库或系统组件。未能给出清单的构建不能算“独立发布”。

## 7. 版本策略

- `0.x`：允许语法和标准库变更，但必须发布迁移说明。
- 稳定版本：采用语言版本、工具链版本和标准库版本分离。
- 破坏性语法变更必须提供格式化器迁移或明确的错误提示。
- 规范中的实验特性必须有开关、警告和退出计划。
