# 风险、阻碍与待决事项

本项目的首要风险不是没有市场，而是实验没有留下可运行成果、协作者无法加入，或个人开发者在范围过大之前失去兴趣。因此风险判断以“能否持续探索和共建”为中心。

## 1. 风险评级说明

- **高：** 不解决就不应进入下一阶段，可能导致返工或项目失败。
- **中：** 可通过原型和限制范围控制，但需要持续跟踪。
- **低：** 有成熟替代方案，暂不阻塞 MVP。

## 2. 风险登记表

| 编号 | 风险/阻碍 | 级别 | 影响 | 缓解措施 | 决策门 |
| --- | --- | --- | --- | --- | --- |
| R-001 | 语法在小例子中漂亮，在真实项目中歧义或冗长 | 高 | 返工 Lexer、Parser、IDE 和文档 | 先写 5 个真实任务，做嵌套和长代码实验 | Phase 0 结束前 |
| R-002 | 语言范围同时覆盖编译器、IDE、运行时和生态 | 高 | 进度失控，无法交付可用版本 | 采用阶段目标和非目标，禁止跨阶段承诺 | 每个版本规划评审 |
| R-003 | 类型系统规则不完整 | 高 | AST/IR/标准库反复重写 | 先写类型规则、错误模型和负面测试 | 对象/模块前 |
| R-004 | 运行时内存和资源生命周期未决 | 高 | Native、WASM、FFI 无法稳定 | 先确定解释器内存模型和运行时 ABI | Native 前 |
| R-005 | 编译器 Parser 与 Tree-sitter 语法不一致 | 高 | IDE 提示和实际编译冲突 | 编译器为语义源，建立兼容性测试 | LSP 发布前 |

| R-007 | “独立发布”缺少平台和依赖定义 | 高 | 用户无法实际运行产物 | 先定义一个主目标平台和干净环境验收 | Native 发布前 |
| R-008 | 标准库不足，用户无法做真实任务 | 高 | 无法验证产品价值 | 先做文件、JSON、时间、CLI，再按案例扩展 | Phase 1 |
| R-009 | 包管理和注册表过早建设 | 中 | 安全、版本和维护负担过大 | 先支持本地模块、路径依赖和锁定文件 | 公共注册表前 |
| R-010 | 只依赖个人维护 | 高 | 语言规范、编译器和生态无法长期演进 | 明确许可证、贡献流程、代码所有权和维护者梯队 | 对外发布前 |
| R-011 | LLVM/平台绑定导致构建困难 | 中 | 开发环境和 CI 不稳定 | 固定工具链版本，先解释器，后 Native | LLVM 接入前 |
| R-012 | 外部依赖和包供应链风险 | 高 | 构建污染、许可证或安全问题 | 校验和、来源、离线缓存和脚本禁用 | 包管理发布前 |
| R-013 | 过早拿成熟语言的生态规模衡量项目 | 中 | 目标失真，开发者失去动力 | 把成熟语言作为参照和互操作对象，不以替代为验收条件 | 每阶段评审 |
| R-014 | 中文 Unicode、输入法和字体造成跨平台差异 | 中 | 解析、显示和诊断不一致 | Unicode 规范化、快照测试和多平台验证 | Lexer/IDE 发布前 |
| R-015 | 性能目标被过早夸大 | 中 | 运行时设计过度复杂 | 先建立基准，不做没有数据的性能承诺 | Native 后 |

## 3. 当前阻碍项目启动的关键问题

以下问题不是“以后再说”的普通待办，而是启动 Phase 0 前最好有负责人和初步答案的事项：

1. **语言名称、源码扩展名和许可证未定。** 影响 CLI、文档、包名、商标和社区。
2. **目标平台未定。** 影响 Go 构建、文件路径、字符显示、运行时和发布测试。
3. **第一批真实用户和任务未定。** 没有用户任务就无法评估语法是否有价值。
4. **类型和错误模型未定。** 影响函数、对象、标准库和 IR。
5. **内存/资源模型未定。** 影响解释器和未来 Native 兼容性。
6. **项目维护方式未定。** 单人项目可以启动；当有外部贡献时再逐步补充审查和发布流程。

## 4. 缺失信息清单

### 产品与用户

- 首发用户是个人开发者、企业内部团队还是教育用户？
- 主要使用简体中文、繁体中文，还是两者都支持？
- 用户是否允许安装本地运行时、编译器和系统依赖？
- 第一版需要处理的 3 个真实项目是什么？

### 语言

- 最终语言名称、文件扩展名、关键字风格和保留字表；
- 是否支持英文标识符与 API；
- 空值、错误、可变性、泛型、接口和并发的计划；
- 数字、文字、Unicode、时区、文件路径和比较的精确定义；
- 兼容性和版本迁移策略。

### 工程

- 主开发平台和首个发布平台；
- 是否接受 LLVM 运行时/动态库依赖；
- Native 与 WASM 的优先级；
- 构建系统、CI 和发布渠道；
- 依赖包的来源、许可证和安全响应机制；
- 是否需要企业私有仓库和离线环境。

### 团队与治理

- 维护者数量、编译器经验和时间投入；
- 代码和规范的审查机制；
- 开源/闭源边界和贡献协议；
- 版本发布、漏洞响应和废弃特性流程。

## 5. 建议决策记录

| 决策项 | 建议 | 暂不决策的代价 |
| --- | --- | --- |
| 实现语言 | 第一版 Go | 同时试多种实现语言会消耗设计时间 |
| 执行顺序 | 解释器优先 | 直接做 Native 会把语义和平台问题混在一起 |
| Parser | 编译器自研；IDE 可用 Tree-sitter | 完全共用编辑器 Parser 会限制语义控制 |
| 类型 | 静态类型为主、有限推导 | 完全动态会把错误推迟到运行时 |
| 循环 | 条件/次数/集合形式区分，变量显式绑定 | 隐含 `当前` 会在嵌套和重构时出错 |
| AI | 只在 IDE 提供建议 | 进入编译器会破坏确定性 |
| 标准库 | 先文件、JSON、时间、CLI | 过早做完整网络/数据库会拉大范围 |
| 包管理 | 先本地模块和锁定文件 | 过早注册表会产生安全和治理债务 |
| 发布 | 先选一个主平台做闭环 | 同时承诺所有平台会掩盖测试缺口 |

## 6. 不能用“继续开发”掩盖的问题

- 语法冲突没有实验数据时，不应靠个人偏好永久定案；
- 没有运行时契约时，不应把 LLVM 接入称作“已经支持编译”；
- 没有干净环境测试时，不应称为“独立发布”；
- 没有用户任务和对照组时，不应称为“比 Python 更高效”；
- 没有许可证和依赖审计时，不应建立公共包仓库；
- 没有维护者和版本策略时，不应承诺长期兼容。
