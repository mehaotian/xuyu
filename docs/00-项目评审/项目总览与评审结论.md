# 项目总览与评审结论

**文档状态：** 整理评审版
**基于材料：** PDR v0.1、工程难度评估、编译器术语说明
**评审结论：** 方向成立，原始范围过宽；建议以“中文编程语言实验与社区共建”重新收敛

## 1. 执行摘要

项目希望探索一门真正可以运行、可以逐步用于开发软件的现代中文编程语言，而不是中文关键字替换器、教学玩具或自然语言 AI 编程器。目标体验包括：中文源码、中文错误信息、中文 IDE 输入辅助、严格语法、解释执行，以及在未来逐步尝试独立编译发布、标准库、包管理和跨平台能力。

这个方向具有清晰的探索价值，但不能把所有长期愿景同时当作第一版交付范围。语言、编译器、运行时、标准库、IDE、调试器、包管理和生态分别都是长期项目；若没有阶段边界，个人或小团队会在还没有得到可运行结果前耗尽兴趣和资源。

**建议的产品判断：**

- 探索问题真实：中文开发者在英文关键字、英文文档、英文错误信息和输入法切换上存在持续摩擦。
- 技术可行：UTF-8、LLVM、WASM、Tree-sitter、LSP 等基础设施可以降低底层实现成本。
- 项目价值不依赖竞争优势成立：中文语法、编译器和工具链的设计过程本身就具有学习和社区研究价值。
- 最大阻碍不是“中文能否解析”，而是语法长期可用性、运行时语义、工具链一致性和生态冷启动。
- 第一阶段应定位为“中文自动化和工具开发语言实验器”，而非“替代 Python、Go、Rust 的完整通用语言”。

## 2. 产品定位

### 2.1 定位陈述

一个以中文为原生源码体验、采用确定性程序语法、支持静态类型和类型推导的开源实验项目。项目通过逐步实现解释器、标准库、工具链和编译后端，探索中文程序语言是否能够形成稳定、可读、可协作的开发体验。

### 2.2 明确不是什么

本项目不应被定义为：

- 把 Python、JavaScript 或 Go 的关键字逐字翻译成中文；
- 依赖自然语言理解或 AI 猜测才能编译的语言；
- 只用于展示中文文化表达的语言玩具；
- 第一版就覆盖系统编程、移动端、游戏引擎、桌面 GUI、云原生和所有平台的万能语言。

### 2.3 目标用户

| 用户 | 主要任务 | 当前价值假设 |
| --- | --- | --- |
| 中文为主的应用开发者 | 写脚本、CLI、API 和内部工具 | 减少语言和文档切换，提升上手速度 |
| 企业内部工具团队 | 文件、数据、接口和流程自动化 | 中文业务概念直接映射到代码，交付独立程序 |
| 有编程基础的学习者 | 学习类型、模块、测试和工程实践 | 中文错误信息和示例降低初始门槛 |
| 游戏/仿真逻辑开发者 | 规则、任务、数值和事件脚本 | 领域对象表达自然，运行环境可控 |
| 现有专业语言开发者 | 评估中文 DSL 或工具链 | 通过 FFI、CLI 和标准库接入现有系统 |

教育、编译器学习和社区共建本身就是项目目标。项目可以从示例开始，也应逐步验证真实任务；但不以用户规模、商业收入或成为主流语言作为必要成功条件。

## 3. 具体使用场景与解决的痛点

### 3.1 优先场景

1. **文件和数据自动化**：批量重命名、目录扫描、CSV/JSON 转换、报表处理。
2. **内部 CLI 和开发者工具**：配置生成、代码生成、发布脚本、运维辅助工具。
3. **轻量 HTTP/API 服务**：小型内网服务、Webhook、数据查询接口。
4. **规则和工作流**：订单规则、审批流程、游戏任务、事件处理。
5. **AI 应用编排**：模型调用、数据清洗和可审计的工作流；AI 只能生成建议，不能绕过编译器。

### 3.2 暂不作为首发场景

- 高性能系统软件、操作系统、驱动和嵌入式；
- 大型桌面 GUI 和完整游戏引擎；
- 需要成熟科学计算、机器学习生态的项目；
- 需要大量第三方包才能成立的生产系统。

### 3.3 痛点到产品能力映射

| 痛点 | 原始设想 | 评审后的要求 |
| --- | --- | --- |
| 中文业务概念与英文代码反复转换 | 中文标识符、一等中文关键字 | 中文标识符合法化，并保证诊断、格式化和调试全链路一致 |
| 中文输入和同音字效率低 | 拼音搜索、补全、纠错建议 | IDE 支持拼音/模糊搜索和候选提示；编译器禁止猜测和自动改写 |
| 英文错误信息影响定位 | 中文错误信息 | 错误必须含位置、原因、期望、实际值和修复建议，且可机器读取 |
| 运行程序依赖 Python/Node/Java | 独立编译和静态打包 | 明确运行时打包策略、平台矩阵和可复现构建，不仅是口号 |
| 新语言缺乏工程工具 | IDE、LSP、测试、包管理 | 先完成 CLI、格式化、测试和诊断，再扩大 IDE 功能 |
| 生态不足 | 标准库、包管理 | 先覆盖少量高价值能力，并提供 FFI/命令行互操作，避免闭门造车 |

## 4. 方案优点

### 4.1 定位清楚且有识别度

“中文原生 + 严格编译 + 独立发布”比“中文关键字”更有产品边界，能够区别于教学语言和纯文化表达项目。

### 4.2 技术路线基本正确

使用 Go 迭代编译器，先实现 Lexer、Parser、AST 和解释器，再抽象 IR，最后接 LLVM/WASM，是降低耦合和快速验证语言语义的合理路径。把 Tree-sitter/LSP 放在 IDE 层、把 AI 放在建议层，也符合确定性编译的要求。

### 4.3 静态类型与类型推导方向合理

静态类型能在运行前发现常见错误，类型推导可减少样板代码。对于面向应用开发的中文语言，这比完全动态类型更适合长期维护。

### 4.4 中文体验被视为完整链路

材料没有把中文局限在关键字，而是覆盖标识符、输入、补全、错误信息、文档和发布，这正是可能形成产品差异的地方。

### 4.5 解释器作为参考实现

让解释器和后续 Native/WASM 后端共享 IR，可以用同一套测试验证语义一致性，降低早期调试难度。

## 5. 不合理或不完整的地方

### 5.1 范围过宽，缺少可交付边界

**问题：** 同时承诺通用语言、编译器、运行时、标准库、IDE、调试器、包管理、Native、WASM 和生态。

**为什么不合理：** 每一项都有独立的设计、测试、平台兼容和维护成本。没有阶段门，开发会在“基础能力尚未稳定”时被工具链和平台问题拖住。

**调整：** 把目标拆成四个产品阶段：语言实验器、可做项目的 CLI、可发布的编译工具链、生态和 IDE。每阶段都设置可验证的退出条件，详见 [技术架构与实现路线](../02-技术设计/技术架构与实现路线.md) 和 [开发计划](../10-开发计划/README.md)。

### 5.2 语法候选被过早当成确定规范

**问题：** `如/否则`、`当/遍/止/跳`、`设置/增加/减少/获取` 等设计很有方向感，但仍存在重载、嵌套作用域、表达式优先级和错误恢复问题。

**为什么不合理：** 语言是否“像中文”不能替代语言是否稳定。一个看似自然的词，可能在泛型、异步、模式匹配或嵌套循环中产生歧义。

**调整：** v0.1 只冻结最小语法；所有高级语法标记为实验性。集合循环必须显式绑定元素名，禁止依赖隐含的 `当前`；计数循环、集合循环和范围循环采用可区分的语法形态。

原始示例中还有几处需要明确收敛：

- `获取 用户.名字` 与普通表达式访问重复，建议先不设为关键字；
- `增加/减少` 更像赋值语法糖或领域操作，必须定义溢出、返回值和可组合性后再冻结；
- `否则` 与 `则` 的职责没有同时保留的必要，应通过用户实验选择一个；
- `定义 玩家` 既可能表示对象类型，也可能表示函数/入口，Parser 必须能从声明形态区分；
- 中文全角冒号、引号和英文符号混用时要有唯一规范化规则，否则格式化、复制和跨平台输入会产生差异。

### 5.3 类型系统只给出方向，没有可执行规则

**缺少：** 可变性、空值、类型兼容、函数类型、泛型、错误类型、数字溢出、集合元素类型、接口实现和模块可见性。

**为什么重要：** 类型系统会决定 AST、IR、运行时、错误信息和标准库 API；后补会导致大规模返工。

**调整：** 在实现对象和模块前先写类型规则与负面测试，不把“静态类型为主”当成足够的规格。

### 5.4 运行时和内存模型未决

**问题：** 材料同时讨论对象、删除、GC、独立打包和异步，但没有决定所有权、垃圾回收、线程模型、异常传播和 FFI 生命周期。

**为什么不合理：** 没有运行时契约，Native、WASM 和解释器的行为无法保证一致，独立发布也无法估算包体和性能。

**调整：** MVP 使用受控托管堆和明确的 GC/资源释放边界；文件、网络等外部资源采用显式关闭或作用域管理。Native 后端前必须完成运行时 ABI 文档。

### 5.5 “不依赖 Python/Node”表述需要分层

**问题：** 用户运行阶段不依赖 Python/Node 是合理目标，但开发阶段的工具链可能使用 Node（例如部分 Tree-sitter/IDE 工具）或 LLVM 依赖。

**为什么需要澄清：** 如果把构建工具依赖和最终程序依赖混为一谈，会导致不必要的技术约束和错误验收。

**调整：** 分别定义“开发者安装依赖”“编译器运行依赖”“产物运行依赖”，并对每个平台给出清单。最终产物只允许依赖目标系统明确列出的运行库。

### 5.6 IDE 与编译器可能出现双语法源

**问题：** 编译器自研 Parser、IDE 使用 Tree-sitter 是可行方案，但两套语法可能不一致。

**为什么危险：** 用户在编辑器中看到的高亮、补全和错误恢复如果与真正编译结果不同，会直接损害信任。

**调整：** 编译器 Parser 作为语义唯一来源；为 IDE 制定兼容性测试。Tree-sitter 仅负责编辑态语法树，所有语义补全和诊断必须调用共享 Language Server 分析结果。

### 5.7 包管理方案过于乐观

**缺少：** 版本约束、锁定文件格式、校验和、镜像、离线构建、私有仓库、供应链审计、许可证和弃包策略。

**为什么重要：** 包管理器一旦进入生产环境，就会影响安全、可复现构建和组织合规，不是几个中文命令的包装。

**调整：** MVP 先支持本地模块和路径依赖；有稳定模块系统后再做公共注册表。

### 5.8 竞品和采用障碍分析不足

**问题：** 原材料强调技术路线，但没有说明用户为什么从 Python/Go/Rust 迁移，也没有量化中文体验能节省多少成本。

**调整：** 首发场景聚焦中文自动化和内部工具，设计对照实验和迁移样例；不以“替代成熟语言”作为早期卖点。

## 6. 建议采纳、暂缓与拒绝的决策

| 决策 | 内容 | 理由 |
| --- | --- | --- |
| 采纳 | 中文标识符、严格语法、中文诊断、UTF-8 | 直接服务核心痛点，技术风险可控 |
| 采纳 | Go 实现第一版、解释器优先、测试先行 | 迭代速度快，便于隔离语言设计问题 |
| 采纳 | AST/语义分析与 IR 分层 | 为解释器、Native、WASM 复用语义 |
| 采纳 | VS Code + LSP 作为早期 IDE 入口 | 避免自研编辑器，降低交付成本 |
| 暂缓 | LLVM 后端、WASM、调试器 | 需先稳定类型和运行时 ABI |
| 暂缓 | 泛型、宏、并发、JIT、插件系统 | 会显著扩大语言和工具链复杂度 |
| 暂缓 | 公共包注册表 | 先解决模块、版本和安全模型 |
| 拒绝 | 编译器根据错别字或自然语言自动猜测 | 破坏确定性、可审计性和安全性 |
| 拒绝 | 第一版同时支持所有平台和所有应用类型 | 无法形成可控验收范围 |

## 7. 成功标准

本项目的成功不是“击败某门成熟语言”，而是每一阶段都留下可运行、可阅读、可复现、可供他人继续参与的成果。

### 7.1 项目与用户层

- 新参与者可以在不熟悉内部实现的情况下运行第一个示例。
- 至少有几个中文示例可以完整演示变量、条件、循环和函数。
- 错误信息能让参与者在不查英文资料的情况下定位常见错误。
- 项目文档、代码注释和实现记录足以让新的爱好者开始修改代码。
- 后续若实现独立发布，再单独验证是否不要求用户安装 Python/Node/Java。

### 7.2 工程层

- 同一份源码在解释器和编译后端的测试结果一致。
- 每个稳定语法特性都有合法、非法、AST、类型和运行测试。
- 编译输出可复现，依赖和工具版本可追踪。
- 编译器不会因机器 locale、输入法或 AI 服务状态改变语义。

### 7.3 建议量化指标

| 指标 | MVP 建议目标 | 说明 |
| --- | --- | --- |
| 首次成功运行时间 | 新参与者 15 分钟内 | 从安装到运行模板项目 |
| 示例完整度 | 每个已实现特性都有可运行示例 | 防止文档和代码脱节 |
| 诊断可行动率 | 常见错误能给出修复方向 | 需要人工维护测试集 |
| 实现可复现性 | 同一版本在固定环境结果一致 | 方便协作和排查问题 |
| 加入项目成本 | 新贡献者能独立完成一个小改动 | 通过贡献演练验证 |

这些指标是验证假设的起点，不是已经证明可达的承诺。
