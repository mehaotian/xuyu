# 技术架构与实现路线

**建议实现语言：** Go
**核心策略：** Interpreter First -> IR -> Native/WASM
**原则：** 语义单一来源、后端可替换、工具链分阶段交付

## 1. 总体架构

```text
中文源码 .中
      │
      ▼
Lexer 词法分析
      │ Token + 源码范围
      ▼
Parser 语法分析
      │
      ▼
AST
      │
      ▼
名称解析 / 类型检查 / 控制流分析
      │
      ▼
自有 IR
   ┌──┼─────────┐
   ▼  ▼         ▼
解释器 Native    WASM
      │   │       │
      ▼   ▼       ▼
开发运行 独立程序 Web 运行
```

IDE 通过 Language Server 复用名称解析、类型检查和诊断；Tree-sitter 只负责编辑态的快速语法树和错误恢复，不拥有最终语义。

## 2. 组件职责

| 组件 | 职责 | 第一阶段状态 |
| --- | --- | --- |
| Token/Source | UTF-8、源码范围、行列映射 | 必须实现 |
| Lexer | 将源码切为 Token，拒绝非法 Unicode 和不确定输入 | 必须实现 |
| Parser | 生成 AST，提供结构化错误恢复 | 必须实现 |
| AST | 表达源码结构，保留必要位置和注释信息 | 必须实现 |
| Resolver | 作用域、符号、模块和属性解析 | 必须实现 |
| Type Checker | 类型检查和类型推导 | 必须实现基础版本 |
| IR | 统一解释器和后端语义 | 第二阶段 |
| Interpreter | 快速运行、参考行为和测试 | 第一阶段优先 |
| Runtime | 对象、文字、列表、I/O、内存和错误支持 | 随标准库演进 |
| Native Backend | 生成独立产物 | 稳定 IR 后接入 |
| WASM Backend | Web/沙箱运行 | Native 后评估 |
| Language Server | 补全、诊断、跳转、重构 | 语言核心稳定后 |
| CLI/Build | 创建、检查、运行、测试、构建、发布 | 必须从第一阶段设计 |

## 3. 技术选择评审

### 3.1 Go 作为第一版实现语言

**采纳理由：** 编译速度快、部署简单、跨平台工具链成熟、团队学习成本相对可控，适合 AST 和类型系统频繁调整的阶段。Go 官方工具链本身也强调规范、构建和文档工具的统一体验。

**限制：** 复杂编译器类型体操、底层运行时和 LLVM 绑定可能需要额外封装；不能因为编译器用 Go 就默认最终语言必须依赖 Go。

### 3.2 Rust 暂缓而非否定

Rust 适合高性能运行时和内存安全组件，但第一阶段最大风险是语言设计变化，而不是编译器执行性能。等 ABI、内存模型和性能热点明确后，再考虑 Rust/C/C++ 组件。

### 3.3 LLVM 后置

LLVM 能解决多架构目标代码、优化和调试信息，但会引入工具链版本、绑定、链接和平台配置复杂度。第一天使用 LLVM 会把语言语义错误和后端错误混在一起，因此必须后置到 IR 稳定之后。

## 4. 语义单一来源

编译器 Parser、解释器、Native 后端和 IDE 必须遵守以下边界：

- 语言规范是行为来源；
- 编译器前端是语义唯一实现；
- IR 是运行和编译的共同契约；
- Language Server 复用前端分析，不自行发明类型规则；
- Tree-sitter grammar 通过兼容性测试，但不能改变编译器语义；
- 解释器是后端一致性参考，不是另一套“方便但不同”的语言。

## 5. 运行模式

### 5.1 开发模式

```text
源码 -> AST -> 检查 -> IR -> 解释器
```

目标是启动快、错误可定位、结果可测试。

### 5.2 发布模式

```text
源码 -> AST -> 检查 -> IR -> 优化 -> Native/WASM -> 产物
```

发布器必须输出构建清单：语言版本、编译器版本、目标平台、依赖、运行时打包方式和哈希。

## 6. 运行时和内存模型建议

原材料正确识别到对象、数组、文件、网络和 GC 是核心难点，但尚未给出最终方案。建议分阶段：

### 6.1 解释器阶段

- 使用托管堆表示文字、列表、映射和对象；
- 先采用简单、可验证的追踪式垃圾回收或受控 arena；
- 外部资源（文件、网络连接、进程）不由 GC 决定关闭，必须显式关闭或绑定作用域；
- 所有运行时错误保留源码调用链。

### 6.2 Native 阶段决策门

在接入 LLVM 前必须完成：

- 值表示和对象布局；
- 字符串、列表和映射的生命周期；
- GC 触发、线程和暂停规则；
- 异常/错误传播 ABI；
- C/系统库 FFI 的所有权；
- 运行时静态/动态打包策略。

如果这些规则未定，Native 后端只能作为实验，不得宣称生产可用。

## 7. IDE、LSP 与输入辅助

建议先使用 VS Code 扩展，而不是自研编辑器。Language Server 提供：

- 中文关键字、API 和符号补全；
- 拼音/编辑距离搜索；
- 基于作用域和类型的候选；
- 中文诊断、跳转、引用和重命名；
- 格式化和项目索引。

输入辅助必须是显式候选。不能把“公鸡”自动替换为“攻击”，也不能把 AI 输出直接送入编译器。

IDE 的最小质量门是：编辑不完整代码时仍能高亮和诊断；保存后编译结果与编辑器提示一致；断网时核心功能仍可用。

## 8. 模块、构建和包管理

### 8.1 顺序

1. 单文件运行；
2. 本地多文件模块；
3. 路径依赖和锁定文件；
4. 版本依赖和缓存；
5. 公共/私有注册表。

### 8.2 最低构建原则

- 默认离线可检查和构建已有依赖；
- 依赖必须带版本和校验和；
- 禁止包安装阶段默认执行任意脚本；
- 记录许可证和来源；
- 提供依赖树和漏洞/撤回信息的扩展点。

## 9. 测试体系

### 9.1 单元测试

Lexer、Parser、符号表、类型检查器、IR 构建器、运行时数据结构。

### 9.2 规范测试

每个语法特性至少包括：合法源码、非法源码、预期 AST、预期诊断和预期运行结果。

### 9.3 差分测试

解释器和 Native/WASM 后端执行相同测试，输出、错误和退出码必须一致或有版本化差异说明。

### 9.4 模糊测试

对 Lexer、Parser、格式化器、Unicode、缩进、嵌套表达式和错误恢复进行 fuzz 测试，避免不可信源码触发崩溃。

## 10. 分阶段路线和退出条件

### Phase 0：语言实验（2～6 周）

范围：关键字、表达式、缩进、变量、函数、条件、循环、列表。
退出条件：至少 5 个真实任务示例，Lexer/Parser/解释器测试稳定，语法冲突清单已记录。

### Phase 1：可用语言核心（2～4 个月）

范围：基础类型、对象、模块、中文诊断、格式化、CLI、文件/JSON/时间标准库。
退出条件：可维护的多文件项目，能完成自动化和 CLI 案例，规范测试覆盖稳定特性。

### Phase 2：可做项目的工具链（4～8 个月）

范围：HTTP、命令行打包、本地依赖、锁定文件、基础 LSP、构建元数据。
退出条件：用户能交付一个可复现的内部工具，干净环境运行产物并有依赖清单。

### Phase 3：Native/WASM 后端（8～18+ 个月）

范围：稳定 IR、运行时 ABI、LLVM 或其他后端、至少一个 Native 目标和可选 WASM。
退出条件：后端与解释器一致性测试通过，发布流程、平台矩阵和性能基线明确。

### Phase 4：生态

范围：公共注册表、包审核、调试器、文档站、插件、治理和社区。
退出条件：不以时间承诺，以活跃项目、维护者数量、包质量和安全流程衡量。
